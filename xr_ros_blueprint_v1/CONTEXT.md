# XR→ROS Blueprint 연구 — Claude Code 전달 문서

작성 기준: 2026-10-02. 아래를 작업 지시로 받아 실행하라. 사용자에게 계획만 제시하고 끝내지 말고, 현재 저장소 확인 → 저장소 자료 확인 → 첫 조사 묶음 → 실행 가능한 첫 pilot까지 진행하라. 실행 예산과 환경 제약은 먼저 명시하고, 결과가 없는 항목은 미확인으로 유지하라.

## 1. 목표와 현재 결정

XR 입력부터 ROS의 물리 실행, 로봇 피드백과 사용자의 승인까지 전체 경로를 지도화하고, 각 사례의 보호 조건·기존 방법·실제 구현·남은 한계를 검증한다. 특정 gap이나 프레임워크의 필요성을 미리 결론으로 두지 않는다.

기존 실험은 전체 문제 중 runtime 입력 활성 증거와 stop/resume 일부를 깊게 검증한 것이다. 해당 독립 gate의 프레임워크 확대 보류가 다른 사례의 연구 종료를 뜻하지 않는다. 이제 40개 사례의 Blueprint를 기준으로 범위를 넓히되, 한 사례씩 기존 방법과 남는 문제를 끝까지 확인한다.

기여 경로는 두 가지 모두 열어 둔다.

- 기존 방법의 정보·신뢰·시간·집행 전제를 실제 배치에서 충족할 수 없어 보호가 성립하지 않는 경우: 그 전제를 확보하는 시스템/방법 후보.
- 개별 기존 방법으로 해결되지만 여러 사례·이질적 구현에서 반복되는 통합 문제를 공통 시스템이 줄이는 경우: 수정량, 정책 재사용, 지연, 오차단, 종단간 보호를 비교하여 시스템 기여를 검증.

그냥 검사들을 묶거나 envelope/gate를 다시 만드는 것은 기여 근거가 아니다. 개별 수정 및 관련 프레임워크의 가장 강한 적용과 비교해야 한다.

## 2. 읽을 자료와 단일 기준

연구 진행의 기준은 이 GitHub 저장소다. 시트는 사용자의 보고·이해를 위한 자료이며, 사용자가 해당 작업에서 명시적으로 요청할 때만 접근한다. 자동 읽기·갱신·동기화하지 않는다. 시트 인증이나 XLSX export는 연구를 진행하기 위한 전제가 아니다.

다음 순서로 저장소 파일을 읽는다.

1. 루트 `CLAUDE.md`: 운영 규칙과 현재 연구 진입점.

3. `xr_ros_blueprint_v1/STATUS.md`: 현재 완료 상태와 다음 작업.
4. `xr_ros_blueprint_v1/CONTEXT.md`: 이 작업 지시 및 이전 결과의 주장 범위.
5. `xr_ros_blueprint_v1/BLUEPRINT.md`: 전체 흐름·위협 모델·사례·계획.
6. `xr_ros_blueprint_v1/data/blueprint.json`: 수정하는 기준 DB. CSV는 재생성하는 검토 뷰.

문헌·코드·실험을 조사할 때 DB, 해당 case 문서, STATUS.md와 다음 handoff를 함께 갱신한다. `python3 xr_ros_blueprint_v1/scripts/refresh_views.py`로 ID 연결 검증과 CSV 재생성을 수행한다. 최신 진행 상황은 Markdown으로 쉽게 읽히게 쓰고, 상세 matrix는 DB로 보존한다.

## 4. 기존 결과 — 재실험 전 반드시 읽을 것

- S1–S5: 필요한 정보가 전달될 때 기존 검사로 해결된 사례. 신규 주장으로 반복하지 않는다.
- P1/P1b: 합성 OpenVR→Gazebo. 메시지 중단 뒤 33–45 mm 잔여 이동, JTC 현재 관절 위치 hold에서 약 1 mm. 명령 차단과 실제 정지는 다르다. deadman·recenter는 증거 전달/기존 앱 수정으로 해결한 범위가 있다.
- P2: 오래된 Ubuntu Monado build의 READY 고착은 알려진 upstream 수정 문제였다. 최신 main의 일반적 사양 위반으로 주장하지 않는다.
- F1: 대역 앱 27회. 독립 runtime 상태 경로 feasibility는 보였지만 timestamp 전제와 비교군 freshness 교란이 있었다. 고정 protocol/raw/result는 그대로 보존하고 사후 해석은 별도 문서에 둔다.
- F2: 대역 앱 27회, 동일 freshness로 비교. interval 검사의 필요성은 중간 중단도 금지하는 정책을 선택할 때에만 추가된다. 상태 검사와 중복·역순 검사 효과는 구분한다. 5 ms 전환과 증거 지연에서 누출이 있었으므로 경계를 제외해 성공을 주장하지 않는다.
- F3: 원본 OpenVR UR5e 앱 1개 + 수정 xrizer + Monado/Servo/Gazebo, 6회. runtime 비활성 구간에 앱이 스스로 명령을 멈춰 수신 gate의 추가 차단 0건. 재개 시 목표가 35 mm 점프했으나 물리적 결과는 특이점 정지에 가렸다. 앱은 무수정이어도 배포 구성요소는 3가지 수정됐고 주기도 50→20 Hz로 변했다.
- 실제 앱에서 `명령 stamp = 입력 sample 시각`은 무수정 상태로 확인되지 않았다. 수신 시점 상태 보호와 sample-to-command 출처 보장은 다르다. runtime token만으로 앱의 명령 계산이 올바르다고 증명되지 않는다.
- 손상 앱 방어는 미완성이다. IPC 제어 권한, 비위조 client 연결, 증거 신뢰, 모든 실행 경로의 매개, 명령 유래를 함께 확인해야 하며 인증 패치 하나로 완료되지 않는다.
- 실제 headset·Quest runtime·물리 로봇, 닫힌 frontend의 내부 읽기는 확인 범위 밖이다. 실제 앱, 대역 앱, 합성 입력, 시뮬레이션, 물리 로봇을 별도 표시한다.

## 5. 사례별로 끝까지 확인하는 절차

각 사례마다 아래 순서로 하나의 case record를 완성한다.

1. 보호 조건을 관측 가능한 문장으로 명시한다. 예: 중단 후 얼마 이내에 움직임을 멈추며, 어떤 조건에서 재개하는가. 정책 선택 자체를 보안 발견으로 주장하지 않는다.
2. 공격자·권한·신뢰 경계와 고장 기준선을 명시한다. 네트워크 공격자, 정상 키의 손상 앱, 정상 전환을 유발하는 근접 공격자, 다른 운영자, 배포 권한자, 비공격 고장을 구분한다.
3. 기존 연구의 보장과 가정, 저자가 명시한 한계의 원문 위치를 확인하고 후속 연구·patch로 해결됐는지 대조한다. 공식 문서/논문 주장/코드/실행/우리 추론을 구분한다.
4. 정보의 제공 가능 → 앱의 실제 읽기 → wire 전달 → ROS 소비 네 단계를 따로 확인한다. 검색에서 못 찾은 것을 부재 증명으로 쓰지 않는다.
5. 가장 강한 기존 방법을 실제 적용한 비교군을 설계한다. 새 후보와 freshness, 정보, 권한, 정책, 부하, 로봇 초기 조건을 맞춘다. 독립 관측의 이점을 비교할 때는 어떤 정보 경로와 신뢰 전제를 추가했는지 명시한다.
6. 실행 전에 protocol을 commit·push로 고정한다. 포함/제외 범위, trial 수, 예상 시간, 성공·실패·유효 trial 기준, 정상 control, 경계 포함 기준과 환경 실패 처리까지 기록한다.
7. 안전한 시뮬레이션/격리 환경에서 최소 재현부터 실행한다. command 차단, controller acknowledgment, 실제 관절/EE 반응을 따로 측정한다. 특이점·충돌 정지가 결과를 가리면 보호 효과로 세지 않는다.
8. 결과를 matrix에 반영한다. 현재 범위의 기존 해결, 구현 누락, 통합 비용, 관측·신뢰·기한 제약, 미확인, 환경 차단을 구분한다. 원리상 가능/실제 구현/비용을 한 판정에 섞지 않는다.
9. 기존 방법으로 해결된 경우에도 저자 한계, 미검증 배치, 후속 해결 상태와 다음 확인을 남긴다. 남는 한계가 곧 우리의 새 gap이라는 결론은 내리지 않는다.

## 6. 작업 순서와 첫 cycle

주차는 작업 규모의 예상이며 실제 장비·코드 접근에 따라 갱신한다. 모든 사례를 한꺼번에 실험하지 않는다.

### W01 — 지도·근거 감사부터 시작

40 사례의 출처와 보호 정책을 점검하고 OpenXR 상태/이벤트·ROS 상태/전환 목록에서 coverage checklist를 만든다. 문헌 검색 DB/검색식/날짜/포함 기준/전문 읽기 수준을 기록한다. taxonomy 작성에 사용하지 않은 구현 하나를 추후 검증용으로 남긴다. 전체 SoK의 완전성을 주장하지 않는다.

첫 조사 묶음은 다음 세 축이다.

- A: 중단·정지·재개 — M2/M3/M4/M5/M6/M39.
- B: 시간·출처·우회 — M12/M17/M18/M19/M20/M40.
- C: 화면·승인과 실행 — M22/M23/M25/M26.

각 축에서 실행 가능성, 기존 근거, 실효 측정 가능성을 확인한 후 첫 1–3개 pilot을 선택하라. 기본 첫 후보는 A의 stop/resume 결합(M39)이며 M3/M5/M6을 하위 사례로 연결한다. 기존 증거를 대체하지 말고 singularity 없는 정상 control을 확보하여 비교 가능성을 먼저 확인한다. A가 환경에 막히면 이유와 대안을 기록하고 B/C의 문헌·코드 감사로 진행한다. 명령이 계속 흐르는 실제 앱 확보를 무기한 반복하지 않는다.

### W02–W03 — 전환과 증거·집행 검증

A에서 complete per-app fix를 먼저 만든다: 입력 중단, controller 정지, 원인별 재허가, 필요 시 새 누름, 재기준화. fresh press가 필요한 정책과 불필요한 순간적 tracking 중단을 구분한다. 공통 manager 후보와 비교할 때 같은 정보·정책·집행 지점을 사용한다.

B에서 sample/생성/발행/수신 시각과 시계 도메인을 구분하고, 상태 효력 시각·관측 지연·짧은 전환·재전송을 검사한다. IPC 권한과 우회 경로는 격리 환경에서 확인한다. 손상 앱을 막는다고 주장하려면 명령 유래까지 포함한 보장이 필요하다.

### W04 — 피드백과 공간·장치 범위로 확대

C는 화면의 물체/점 선택 같은 목표 지정형으로 시작한다. scene/object version 검사라는 기존 baseline을 먼저 적용한다. 연속 제어의 고전적 지연 문제와 구분한다. 표시·선택·명령의 관계를 관측할 수 있는지 확인한다.

M7/M8/M9/M10/M28/M29/M38은 공간·장치·다중 입력의 코드 감사→최소 실험 순서로 진행한다. recenter, calibration, drift, tf 위조는 원인과 방어 범위가 다르므로 합치지 않는다.

통신·privacy·availability(M15/M16/M30/M31/M32/M35/M36)는 제한된 별도 묶음으로 최신 방어·patch를 조사한다. 핵심 teleop 보장과 공통 근거가 약하면 보조 트랙으로 남긴다.

### W07 — 근거가 생긴 시스템만 제작

반복되는 문제와 공통 설계가 확인되면 작은 prototype을 만든다. 최종 시스템 평가에는 서로 다른 실제 경로 최소 2개, 가장 강한 개별 수정, 관련 프레임워크, 작성에 쓰지 않은 사례/구현을 포함한다. 환경이 부족하면 검증 단계의 한계로 남긴다.

수정 파일/의미 있는 코드 변경량, 정책 재사용과 추가 정책 비용, 배포 구성요소 수정, 지연 분포, 정상 오차단, 위험 통과, 실제 정지·재개 결과를 함께 측정한다. ROS 쪽만 수정 0으로 세지 말고 XR 원천/transport/runtime/controller까지 전체 비용을 센다. method gap이 없어도 통합 이득이 입증되면 시스템 기여 후보로 유지한다.

## 7. 버전 관리·보고

자료/schema, 코드 감사 묶음, protocol freeze, 실행/raw, analysis/decision을 각각 checkpoint로 commit·push한다. push 성공 후 local HEAD와 해당 원격 branch SHA의 일치를 확인하고 STATUS.md에 기록한다. push가 실패하면 실패 이유와 로컬 SHA를 보고하되 성공으로 쓰지 않는다. force push나 다른 작업 branch 병합을 하지 않는다.

기존 frozen 자료는 수정하지 않는다. 정정은 새 문서에 출처 commit과 변경된 주장 범위를 기록한다. 대용량 raw는 저장소 정책을 따르고 추적 가능한 위치·hash를 남긴다. 장비/host 설치, 외부 개발자 연락 등 별도 권한이 필요한 작업은 구체적인 변경을 정리한 뒤 사용자에게 요청한다. routine code/read-only/격리 실험/commit-push는 승인된 연구 범위에서 진행한다.

상황과 context는 GitHub 파일에 갱신한다. 시트는 사용자가 명시적으로 요청할 때만 접근한다. DB/case/STATUS/CONTEXT를 서로 연결하고 다음 세션이 파일만 읽어도 계속할 수 있게 한다.

첫 보고는 다음을 포함하라.

1. 시작 HEAD·branch·보존 상태·원격 checkpoint.
2. 읽은 저장소 자료의 판본과 실제 읽은 원문·코드 범위.
3. A/B/C의 현재 근거와 첫 pilot 선택 이유.
4. 실행 전 고정한 protocol 및 정상 control 확보 결과.
5. 실제 실행과 결과, 교란/미실행, 기존 방법 적용 결과.
6. 갱신한 case/matrix/limitation ID와 다음 독립 작업.

특정 사례가 기존 방법으로 해결되면 그 사례를 기록하고 다음 후보로 진행한다. 환경 실패를 공백 부재로 판단하지 않는다. 모든 사례가 해결될 가능성도 열어 두되, 반복되는 미관측·신뢰·집행·통합 비용을 근거로 검증한다.
