## 3. Source-state-command lineage and B0-shim equivalence

Docker: the receiver's actual parsed state object is bound to a synthetic source sample ID, generation ID, native `isTracked`, source monotonic time and exact wire payload. Each cached-state publication gets a child ID. In the same composed original classes, exact canonical ROS fields join the receiver publication to the mapper callback and mapper publication to the bridge callback; bridge `TwistStamped` publication receives a derived command ID. `docker_hold_01` recorded 3,153 publications, 2,102 exact callback joins, zero ambiguous joins and 1,052 receiver publications. Multiple receiver publications can therefore be tied to one cached input. Neutral/timeout publications have an explicit original-neutral parent, rather than an invented sample ID. This is exact **through bridge publication in this B0-shim process**, not proof of individual MoveIt Servo callback acceptance, downstream command-to-joint causality, or native Quest semantics. The original B0 process has no such IDs.

OpenVR: `inputs/openvr.py` wraps the existing deterministic fake API; each actual `getDeviceToAbsoluteTrackingPose` call stores a sample ID, generation, raw matrix, `bPoseIsValid`, `eTrackingResult`, grip and monotonic time. `openvr_production.py` wraps only the original program's PoseStamped publisher. `openvr_shim_01` bound all 90 observed production poses to distinct fake API polls. This is exact through the production publisher, **not** through the Servo callback or trajectory controller. OpenVR fake state is not actual Quest/ALVR state.

The B0/shim positive controls did move Gazebo: Docker active excursion B0 `.278028 rad`, shim `.276970 rad`; OpenVR B0 `.209774 rad`, shim `.213396 rad`. Final per-joint differences were `.000633 rad` Docker and `.014141 rad` OpenVR, each below the frozen `.02 rad` output tolerance. However, source-index relative scheduling differed by a maximum `8.001 ms` Docker and `12.630 ms` OpenVR; OpenVR poll counts were 405 versus 402. The frozen >5 ms condition makes both pairs **INVALID_COMPARISON** for formal B0-shim equivalence. Similar output is an observation, not qualification PASS. A pre-barrier source index and matched 50 Hz schedule need stronger ACK/scheduling control before comparison.

## 4. Docker stop and re-arm

All trials start from the registered Gazebo arm pose and include a moving active phase. `docker_external_01` called Humble `/servo_node/stop_servo` (`std_srvs/srv/Trigger`) while moving. The service returned success, and controller command publication stopped, but the velocity controller retained the last nonzero command: arm displacement in the next 1 s was `.147516 rad`, no qualifying settled window occurred. Thus **Servo stop alone failed the registered halt contract**. It must not be credited as a stop adapter success.

`docker_hold_01` then combined the same stop call with one explicit all-zero `Float64MultiArray` to `/joint_group_velocity_controller/commands` at 12.03 ms after the operator trigger. The first 1 s contained one zero controller command, no nonzero controller commands, and the arm settled by 520.20 ms; trigger-to-1 s displacement was `.003487 rad`. The normal active phase had `.260806 rad` excursion. The bridge **continued** generating 60 nonzero Servo-input twists in the first second after stop; the controller-side interlock stopped their downstream effect. This does not satisfy a claim that the unmodified source stopped producing commands. After a .6 s release and new reference, Docker's reference phase stayed at idle-scale movement, and the resumed phase moved `.366622 rad`. This qualifies the external stop+zero and new-reference mechanism for this synthetic trial only. R_EXPLICIT/R_AUTO policy enforcement and a robust input-side hold remain unverified.

`docker_stall_03` stopped sender bytes after active movement. Receiver timeout neutralized; within the first stall second only 13 of 61 Servo input twists were nonzero, last at about 199.93 ms after stall start, and one nonzero controller output was observed 0.607 ms after the exact last-receiver-observation+250 ms trigger, followed by zero output. The arm was settled by 539.59 ms after that trigger, with .004685 rad maximum post-trigger joint displacement in 1 s. The original receiver closed the idle TCP connection; the harness reconnected and used generation 2. The earlier failed attempts (`stall_01`: overlay assertion, `stall_02`: harness BrokenPipe on the expected receiver disconnect) are retained, not removed. This is native sender-timeout behavior, separate from external stop+zero.

## 5. OpenVR stop, hold and re-arm

The actual Jazzy API exposed `/servo_node/pause_servo [std_srvs/srv/SetBool]`; `ur5_arm_controller` was active as `joint_trajectory_controller/JointTrajectoryController`. Both trials started with normal fake API movement. `openvr_stop_01` received a successful pause response, but the arm still traveled `.066800 rad` in the following 1 s and had no qualifying settled window by 1 s. There were no new trajectory publications during that second, while 50 source production poses still reached the Servo input topic. The already delivered trajectory/controller response remained consequential.

`openvr_hold_01` added one short (50 ms) **current measured joint-position** trajectory with zero target velocities after pause; it did not send a zero absolute pose. One hold trajectory was recorded. Post-trigger 1 s displacement was `.018601 rad`; the first qualifying .5 s settled window ended at **1,203.14 ms**, beyond the frozen 1 s limit. Therefore OpenVR stop/hold **does not PASS** the registered halt criterion, despite a markedly smaller displacement and later stable joints. After grip release and unpause, the original program recaptured its reference, but the `new_reference` phase itself moved `.216495 rad` and subsequent `resumed` phase moved `.236907 rad`. The new reference cannot be called jump-free or automatically safe. No controller deactivation/cancel semantics or independently enforced re-arm policy were qualified.

## 6. Clock and start barrier

`analysis/clock.json` contains 50 host-bracketed monotonic samples per image. Host and both containers had boot ID `37a3af0a-4c25-46ee-b682-eeca0be31c48` and time namespace `time:[4026531834]`. Zero offset lay within every bracket; maximum half round-trip uncertainty was `.078887 ms` Humble and `.063504 ms` Jazzy, inside the frozen 1 ms uncertainty bound for these probes. Sender, recorder, health adapter and in-process lineage logs use monotonic nanoseconds; ROS header stamps remain separate wall/ROS time. The official generated monitor's status log has wall time only, so its exact internal decision instant cannot be subtracted from the monotonic source timestamp; the adapter's monotonic observation instant is the bounded event used for stop timing.

The recorder observed at least 0.5 s of named `/joint_states`, ≥3 increasing header stamps, starting position error Docker `.00002721 rad` and OpenVR `.00000573 rad`, velocity below `.001 rad/s`, drift below `.0001 rad`, before releasing `barrier.json`. Controller lists/services and MoveIt Servo logs were captured. OpenVR production spin waited behind that file and fake poll index began afterward. However, Docker `production.ready` is a launcher marker after a fixed startup sleep and graph listing, **not an ACK from every original subscriber or Servo/controller that a recorder match exists**. The recorder also did not verify all expected ROS subscriptions through DDS before release. Thus the integrated joint readiness component passed, while the complete preregistered common start barrier remains **PARTIAL/BLOCKED_INTEGRATION**. The B0/shim >5 ms source timing failures confirm that matched input start conditions are not yet reproducible for formal comparisons.

`docker_health_01` ran the unmodified official generator output inside the owned Humble Gazebo container with its configured oracle absent. A separate `health_stop.py` published one `ReceivedPoseStates` stimulus on the monitor's configured input. The monitor's own status recorded `verdict_raw=unknown`, `decision=forwarded` (native fail-open). Only that **health status**, not the message tracking value, source age, generation or recovery policy, triggered the adapter. The adapter requested `/servo_node/stop_servo` 6.67 ms after it observed the unknown event, received success, then published zero velocity at 7.20 ms. The controller recorded one zero command, no nonzero commands in the following 1 s; Gazebo settled by 527.28 ms from the external health trigger. The original bridge still produced nonzero Servo-input twists.

This demonstrates a **B2-composed health-to-controller-stop path** for one declared stimulus, not a full filter installed in the original input→controller path and not a B2 performance result. The monitor's fail-open event and the composed stop are distinct logs (`raw/docker_health_01/rosmonitoring/.../custom_status.jsonl` versus `health.jsonl`). A true oracle policy-violation stop, oracle-disconnect and timeout stop, missing-heartbeat watchdog, and the same health contract on OpenVR are still UNKNOWN. Nothing here changes B2-native behavior or attributes composed stop to ROSMonitoring itself.
